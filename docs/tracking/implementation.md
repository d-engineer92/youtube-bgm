## 依頼する作業

[TRK-001](README.md)を入口とし、TRK-002〜006とARC-002/POL-001を必要な作業に応じて読む。別実装PRで、新着を含む全取得動画の自動追跡・履歴表示・最小出力・安全なリセットを実装する。元の新着取得を削ったり、低再生の足切りを追加したりしない。

順序は以下。各段階は今回の一つの改修であり、追跡の登録だけで完了にしない。

1. 既存コードと実効DB構成を確認し、全取得経路、観測FK、期限処理、キュー/予算、通常起動を一覧化する。
2. 初回観測と自動追跡の原子的登録、日次枠の更新・履歴追記・再試行・終了条件・予算を実装する。
3. 時系列/差分/欠測/稼働状態の画面とJSON/CSV、固定考察プロンプトの参照を実装する。
4. 専用テストDBで既存回帰・下記受入条件・ブラウザー・実プロセス停止からの復旧を検証する。
5. 監査P0とG01〜G09の専用PostgreSQL合格後、TRK-004の一回限りの切替を対象ローカル環境で実施する。既切替なら再消去しない。旧調査データを引き継がない。
6. 新方式の初回探索・全自動追跡登録を実APIで確認する。実翌日観測はその時点での確認状況を別に報告する。

実装対象：Collector、ApiCaller、Retention、Presentation、Planner/Runner、対象モデルとmigration、routes/console、DBキュー、Compose、既存一覧/比較と追加の小さい時系列表示、README/必要仕様。LA-1/LA-2は回帰のみで機能拡張しない。

## 実装で特に確認する既存箇所

- `Collector::refreshWatch()` がwatchedのみを選ぶこと。新規発見の追跡登録は現在存在しない。
- `observations` がfetch_run削除にcascadeすること。期限と履歴の独立性が必要。
- `Retention::prune()` による探索期限・対象孤児削除を、新しいアクティブ追跡と整合させること。
- 共通予算台帳 `api_days` をリセットしないこと。DBを消してもGoogle側の使用量は戻らない。
- `Presentation::dailyDelta()` だけを変更しても、実際の観測点が作られなければ要件未達であること。
