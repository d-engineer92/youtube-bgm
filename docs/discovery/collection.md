# 探索の収集計画・API・復旧

> 文書ID：EXP-003  
> 状態：追加実装仕様（未実装）／2026-10-14  
> 読む場面：プランナー、API呼び出し、ジョブ、進捗、再開処理。

## 1. 固定する検索計画

[カタログ](seed-catalog-v1.json)の8テーマから、選択プリセットのprimaryを一つずつ使う。開始時刻T0をUTCの日時として確定し、辞書版・検索語・フィルターを実行に保存する。再開時にT0や語を現在値へ差し替えない。

| 条件ID | 調査目的 | API条件 | 初回 |
|---|---|---|---|
| recent_views | 最近公開された目立つ作品 | publishedAfter=T0-30日、publishedBefore=T0、order=viewCount | 全8テーマ |
| recent_new | 上位作だけに偏らず新着も見る | 同期間、order=date | 全8テーマ |
| older_reference | 古い作品の参考例を探す | publishedAfter=T0-5暦年、publishedBefore=T0-180日、order=viewCount | 任意の追加ボタン |

共通：part=snippet、type=video、videoDuration=long、maxResults=10、regionCode/relevanceLanguageはプリセット由来。既定はen-US={US,en}、比較用ja-JP={JP,ja}。国の同時総当たりはしない。音楽カテゴリ・年齢・登録者数の足切りは既定で追加しない。

- `long`は20分超であり1時間以上ではない。初期の探索対象は長尺に限定するが、全BGM需要を網羅しない。詳細操作で尺条件を変えたら別のタスクとして記録する。
- live/upcomingは既定の比較一覧から別枠へ。既存のbroadcast_status・has_live_detailsを利用し、ライブ履歴ありと通常動画を黙って混ぜない。unknownは不明と表示する。必要な情報は保存し、全件結果から確認可能にする。
- 8テーマを一巡してから次の条件へ進む順で計画し、特定の1テーマだけで予算を使い切らない。
- 初回16検索ページ、最大160検索ヒット。160本のユニーク動画は保証しない。追加ページは初回には追わない。空のページやライブ除外後の不足を埋めるための自動追加取得もしない。
- 関連語の深掘りは1語・recent_viewsの1ページが既定。新着・古い作品への切替も明示操作で追加する。
- 深掘りはparent_exploration_idを持つ新しい小さな実行として記録し、完了済み初回runの予算や条件を上書きしない。共通の日次枠は同じものを使う。

## 2. 既存実装を利用する際の注意

確認したmainの `ResearchController::search()` はq必須、`Collector::searchParameters()` は地域・関連言語を渡していない。旧手動検索は維持し、探索入口では利用者入力ではなく保存済み条件からqを解決する。GoogleGatewayまでUS/enまたはJP/jaが届くことをテストする。

内部のUTC日時を、既存の手動フォーム用JST日付パース・endOfDayに再変換しない。UTCの確定条件を扱う正規化層を追加し、手動フォームの既存挙動は回帰テストする。

`Collector::pages()` はページトークンと取得IDを保存してから詳細取得する。一方、取得上限で止まったrunがcompleteでもlisting_done=falseの場合がある。探索では「1ページ取得と当該IDの詳細解決まで完了」と「YouTube検索結果を最後まで取得」を別に持つ。既存resumeを無条件に呼んで2ページ目を取らない。

必要な拡張：検索条件の地域/言語、1ページ制限、検索ヒット順/ID、探索タスクとFetchRunの結び付け、検索済みIDの詳細取得だけの再開。既存API/保存コードをコピーして別系統のコレクターにしない。

## 3. 非同期処理

Web POSTは実行計画を保存・キュー投入して進捗画面へ戻す。全16検索をHTTPリクエストの中で同期実行しない。

LaravelのPostgreSQL DBキューと単一ワーカーを使う。必要なjobs/failed_jobsテーブルとComposeサービスを追加してよい。Redis・SQLite・外部キュー・新規VPSは不要。キューpayloadは内部ID中心とし、APIレスポンスやキーを複製しない。

1タスクは検索1ページと動画/チャンネル詳細の解決。次タスクへ順次進む。停止/枠不足では自動無限再投入せずpausedにする。DBトランザクションをネットワーク呼び出しの間ずっと保持しない。

worker timeout < retry_after < claim/lease期間等の整合を設定し、YouTubeコレクターの既存ロックと競合しても二重実行しない。busyは待機として上限付きで扱う。キューワーカーが処理中に失われても、lease失効後に同一task/FetchRunから復旧する。Webから任意シェルを起動しない。

## 4. API予算

確認した `config/youtube.php` はアプリ上限が検索20回/日、read500回/日。今回その既定を無断で上げない。初回計画16ページで、残りは深掘りや再試行に使う。既に使った枠があれば計画の途中で止まってよい。

公式既定枠とアプリの節約上限は別。2026-10-14の公式本文ではsearch.listは専用100回/日、他の読み取り等は別枠であり、実プロジェクトはCloud Consoleで確認する。[出典](sources.md)

既存ApiCaller/API日次台帳をすべての入口で共有する。探索だけ別のカウンターにして、手動検索・URL登録・既存ウォッチと合わせた上限を抜けない。再試行・ページ追加も消費する。クォータ日の境界はAmerica/Los_Angeles、画面はJST換算時刻も表示する。

- 初回のrun単位上限：検索attempt 20、read attempt 100。各API送信前に日次上限とrun上限を永続カウンターで検査・計上する。
- プランナーの外側でCollectorを呼ぶだけでは、Collectorのresetで操作カウンターが戻る。run単位予算はresetを跨いでも残るようApiCallerの呼び出し境界へ統合する。
- 上限到達時は途中結果を表示して停止。条件を隠して変える、別キーへ切り替えるなどの回避は行わない。計画16タスクのうち何が未実施か示す。
- 日次枠の停止は翌日以降に同じrunを明示再開可能。run上限自体を使い切った場合は同じrunの予算を黙ってリセットしない。残った条件だけを新しい明示実行で再計画し、元runの参照と未完了理由を残す。
- この台帳はアプリの送信試行記録であり、同じCloudプロジェクトを外部から使った分の厳密な残量ではない。HTTP送信直前後の強制停止は消費不明として保守的に計上し、「APIが必ずexactly-once」とは約束しない。
- 429/5xxは既存の上限付き再試行。キー不備/権限不足/quotaExceededは検索語を変えず停止し、原因を表示する。

## 5. 状態と再開

実行：queued → running → complete / partial / paused / failed / expired。  
タスク：pending → running → complete / empty / partial / failed / skipped。

completeは計画したスコープの完了。emptyはAPI成功で0ヒット。詳細未返却はunavailable、エラーによる未取得とは区別する。1タスク失敗が他テーマの成功結果を破棄しない。

実行とタスクの一意キーをDB制約で保証する。開始ボタンのidempotency token、同一runの重複キュー投入、画面更新、ワーカー再開で新しい探索を重複作成しない。完了済みタスクは再取得しない。

検索ページを保存済みなら詳細取得だけを再開する。送信後保存前に落ちた場合は再送の可能性を記録し、ID重複排除と試行上限で封じる。pageToken失効は同じ範囲を勝手に先頭から無限再検索せず、新規の明示実行を案内する。

辞書変更後も実行中の条件は固定。期限切れrunは再開不可。既存の公開情報・観測を消してやり直す操作はしない。自動の日次『新規探索』は初回OFF、既存ウォッチの日次更新は維持する。
