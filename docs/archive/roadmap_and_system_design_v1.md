# YouTube AI×BGM：収益化ロードマップ・システム設計 v1

作成日：2026-10-14（Asia/Tokyo）
状態：実装前の設計案。アプリの実装・実環境への導入・API疎通・音源の試聴比較は未実施。

## 1. 目的と今回の判断

目的は「動画を大量に作る」ことではなく、利用シーンの明確なBGMを制作し、視聴者の反応を検証しながら、制作費と運用負荷に見合う収益を得ることである。

初期構成は、1チャンネル、1つの主な利用シーン、手動での音源選定・公開判断を基本とする。競合リサーチ、制作素材と利用許諾の管理、動画レンダリング、自チャンネル実績の取り込みを段階的に実装する。収益化の時期・金額は保証しない。最初の90日は「収益化期限」ではなく「事業仮説と制作工程の検証期間」とする。

音楽サービスの最初の比較候補はStable AudioとSuno。Stable Audioは低額プランとDL上限なしが比較理由。SunoはPremierのStudio経由の公式書き出しにDL上限がないため、全面的に除外しない。音質・使いやすさ・採用率の比較はこれから実測する。

## 3. 先に決める運用上の境界

### 3.1 初期に行うこと

公開情報の取得、少数の競合比較、本人の考察メモ、制作指示書、音源・画像・権利証跡の登録、音量調整・曲つなぎ・動画化、YouTube Studioへの手動投稿、Studioから本人が書き出したレポートの取り込み。

### 3.2 後から追加すること

独自スコアと長期の競合履歴は、YouTubeの派生指標・保存条件の適用手続きと許容範囲を確認してから有効化する。自チャンネルのAnalytics/Reporting API連携と自動アップロードは、OAuthを追加する方針に変更した場合だけ実装する。

### 3.3 初期には行わないこと

多チャンネル同時立ち上げ、24時間ライブ、音楽配信サイトへの同時展開、音源販売・素材ライブラリ配布、Content ID登録、他人の音源・画像の再利用、非公式APIや自動クリックによるDL制限回避、無人での自動公開。

これらは「永久に禁止」という事業判断ではない。目的に対する優先順位・追加の利用許諾・運用リスクを切り分けるための初期スコープである。

### 4.2 商用利用の確認票

生成サービスへの確認文例：

> 自分が生成した歌詞なし音楽を、自作の静止画または簡単な映像と組み合わせ、音楽の鑑賞・作業用BGMを主目的とした30〜60分のYouTube動画として公開し、広告およびYouTube Premium収益を得る予定です。他者への音源再配布や素材販売はしません。この利用が希望するプランで許可されるか、生成時・ダウンロード時の契約条件、解約後の継続公開、Content IDの制限も含めて確認したいです。

「動画の背景に使える」「音楽自体を配信できる」「音源を他人に販売できる」「Content IDに登録できる」を別々に記録する。商用利用の許諾は、著作権が必ず成立すること、第三者の権利を絶対に侵害しないこと、YouTubeの収益化審査に必ず通ることを保証しない。

Stable Audioの説明・価格は確認できたが、Webアプリの契約全文を今回の取得結果から完全には検証できていない。音楽主体の公開用途が契約に適合することを確認してから商用公開する。

### 4.3 試作の評価方法（提案）

同じ制作指示書で各候補10テイクを比較する。サービスごとに最適なプロンプト形式へ調整してよいが、目指す用途・楽器・テンポ・尺は揃える。未採用も記録する。

評価項目は、用途への一致、意図しない歌声、音割れ、急な音量変化、曲構成の破綻、終端の切れ方、手直し時間、採用できた尺。主指標は「採用可能な音源1分あたりの費用」、補助指標は採用率と修正時間とする。無料試聴の出力は、後から課金すれば商用化できるとは仮定しない。

必要量の計算：

```
必要な新規採用尺 = 動画本数 × 動画尺 × 新規音源比率
必要な生成尺 ≈ 必要な新規採用尺 ÷ 採用率
必要なDL曲数 ≈ 必要な新規採用尺 ÷ 採用曲の平均尺
```

例：毎月60分×8本、すべて新規音源、平均4分、採用率30%なら、約120曲の採用・約400曲分の生成が必要になる。曲間クロスフェード分を考えると若干の余裕も必要。この条件ではSoloの約165回で足りると約束できない。月額だけでなく制作量からプランを選ぶ。

## 5. 収益化ロードマップ（提案）

### フェーズ0：開始〜1週目／権利・費用・用途を絞る

候補用途を3つまで出し、継続して制作できる1用途を選ぶ。例は「夜間のコーディング」「読書」「静かなカフェ作業」。これらの需要は未検証であり、人気ジャンルと断定しない。ユーザーの経験から夜のコーディングを仮説候補にすることは合理的だが、選定はリサーチと試聴で行う。

制作費の上限を先に置き、音楽サービスを試す。競合は20チャンネル程度から始め、規模が大きいものだけでなく小規模・伸び悩み例も比較する。成功例だけを抽出して再現性を結論づけない。

完了条件：用途、リスナーの場面、音楽の方向性、画像の方向性、許諾、許容費用、試作結果が記載された1枚のチャンネル企画書がある。

### フェーズ1：2〜4週目／最小構成で公開する

少数の30〜60分動画を制作し、無理なく可能なら累計4〜6本を試す。本数は義務ではなく、毎回全編確認できることを優先する。1本の中で冒頭の音楽・サムネイル・タイトルの用途を一致させる。

公開前に、全素材の利用許諾、意図しない歌声、接続部、音量、動画の途中終了、説明欄、AI利用の申告を確認する。YouTube Studioで非公開アップロードし、チェック結果と完成動画を確認してから公開する。アップロード時点で申し立てがなくても将来の申し立てがない保証にはならない。

システムは競合一覧、制作台帳、権利台帳、音源登録、FFmpegレンダリングだけでよい。自動アップロードの完成を待たない。

完了条件：制作〜公開までの工程を再実行でき、所要時間・消費クレジット・採用率が分かる。

### フェーズ2：5〜8週目／反応を比較する

公開後7日・28日などの同じ経過時点を揃え、動画尺、流入元、企画の違いを記録する。公開直後と数か月経過した動画の累計再生を単純比較しない。

一次指標は動画ごとの視聴時間と平均視聴時間、補助指標はサムネイル表示・CTR・登録者獲得・コメント等。CTRだけを上げて視聴満足を下げない。露出が少なすぎる場合は失敗と断定せず、観測不足とする。

サムネイルとタイトルのテストはStudioのネイティブ機能を優先する。公式テストはCTRだけでなく視聴時間を重視する。一度にすべての要素を変えず、仮説と変更要素を記録する。[S14]

完了条件：少なくとも1つの仮説について、支持・棄却・保留の理由を説明できる。

### フェーズ3：9〜12週目／継続できる型を作る

複数回の動画で反応が再現するか確認し、安定して制作できるペースだけ増やす。単発の大再生だけで新規サービスの年契約や大規模サーバー契約に進まない。反応が弱い場合は「露出」「入口」「視聴後の満足」「制作費」を分けて原因候補を見直す。

自チャンネルのCSV分析と改善記録を使い、月次の制作費・売上・作業時間を整理する。

完了条件：継続、用途の見直し、制作工程の改善、一時停止のいずれかを根拠付きで選べる。90日以内の収益化は必須条件ではない。

### フェーズ4：条件達成後／審査・収益化・入金

2026-10-14時点の長尺中心の広告収益化要件は、登録者1,000人と過去12か月の有効な公開動画の視聴時間4,000時間。公式には2027-02-01から、新規参入の広告・Premium向け要件が登録者1,000人と過去365日8,000時間へ変更されると案内されている。すでにYPPに参加しているチャンネルの扱いは個別の公式案内を確認する。[S10–S11]

登録者500人等による早期のファン支援機能は、広告収益の条件とは別である。数値達成だけで審査通過は決まらない。確認の正本はYouTube Studioの収益化タブとする。

日本円のAdSense支払基準額は8,000円。収益の発生と入金は別の節目。本人確認、支払い情報、必要な税務情報なども完了させる。[S15]

## 6. 費用と売上のモデル

最初の予算は本人が決める。以下の5,000円は試算用の仮定であり、実際のサービス料金合計の見積もりではない。

```
月間収益 = 月間視聴回数 ÷ 1000 × 実測RPM
月間現金収支 = 月間収益 − 月間サービス費 − 保存/計算/その他費用
必要視聴回数 = (目標現金収支 + 月間費用) ÷ 仮定RPM × 1000
```

月間費用5,000円、目標現金収支50,000円なら必要売上は55,000円。RPM100円なら55万回、300円なら約18.3万回、600円なら約9.2万回、1,000円なら5.5万回。すべて仮定の感度分析であり、BGMジャンルの標準RPMを示していない。税金・本人の労働費は未控除。

StudioのRPMはYouTube分配後の収益を基準とするため、同じ分配率をさらに差し引かない。広告以外の収益を含む場合は二重計上しない。[S16]

## 7. 判断軸A/Bの実装方針

| 元の判断軸 | 設計上の扱い | 注意点 |
|---|---|---|
| 勢い | 観測時刻間の再生数差分。必要なら経過時間で割る | 1日間隔の差分/24は期間平均でありリアルタイムVPHではない |
| 効率 | 動画再生数/登録者数は比率として扱い、推薦獲得率とは呼ばない | 登録者数は丸められ、分母の時点でも値が変わる |
| 突出度 | 同程度の公開経過日・同条件動画との比較。3倍は仮のパラメータ | 少数サンプル、中央値0では判定不能。独自判定は許容範囲確認後 |
| 再現性 | 開設日・最古の確認可能公開動画・初回観測日を区別 | 削除・非公開・過去の運営変更は公開APIだけでは復元できない |
| 持続性 | 直近複数作を同じ公開経過時点で比較 | 1作の累計が大きいだけで持続需要とはしない |
| 登録率 | 自チャンネルでは同期間の登録獲得/再生、競合では公開値の比率に限定 | 競合の総登録者/総再生は本当の登録コンバージョン率ではない |
| 中身・コメント | コメントの利用場面、要望、不満を根拠付きで読む | コメント投稿者は全視聴者の無作為標本ではない |
| 季節適合 | 季節・曜日・時間帯を仮説属性として記録 | 視聴者の国不明の競合に日本時間の曜日だけで理由を付けない |
| タグ・一貫性 | タグ、タイトル、説明の記述と人による観察を区別 | タグでアルゴリズムに乗ったと断定しない |
| サムネイル | 構図・用途の伝わり方を比較し、自チャンネルでテスト | 伸びた理由についてのAI説明は仮説。画像の転用はしない |

数値不足は0ではなく「不明/不足」。API非返却・非公開・コメント無効も別の状態として持つ。日次のマイナス差分は集計訂正等の可能性があるため勝手に0へ補正しない。

判断軸Bには、需要・持続性に加えて「適法かつ許諾内で制作可能か」「既存作品のコピーではない価値を出せるか」「予算と時間の中で継続できるか」を加える。

### 仮説レコード例

- 観測：複数の参考動画に、音量が安定していることを評価するコメントがある。
- 仮説：対象リスナーは、刺激の少ない連続した音場を求めている可能性がある。
- 変更：次の自作動画は接続部の音量と急な音色変化を重点的に抑える。
- 評価：同程度の尺・公開経過日・流入元で平均視聴時間等を比較する。
- 制約：楽曲そのものや露出の差もあるため、この1比較で因果を確定しない。
- 結論：支持/棄却/保留、次の観測・変更内容を保存する。

## 8. APIの役割と取得できないもの

| 用途 | 初期方式 | 認証 |
|---|---|---|
| 新規動画・チャンネル探索 | Data API search.list | APIキー |
| 基本情報・公開統計 | channels.list / videos.list | APIキー |
| 投稿一覧 | uploadsプレイリスト → playlistItems.list | APIキー |
| 公開コメントの取得 | commentThreads.list、必要な範囲のみ | APIキー |
| 自チャンネルの維持率・視聴時間・収益 | Studio CSVを手動インポート | アプリはOAuth不要 |
| 自分の詳細実績の自動取得 | 将来Analytics API / Reporting API | OAuthを追加 |
| 動画投稿・予約・更新 | 初期はStudio手動、将来Data API | APIによる操作はOAuth必要 |

公開APIでは競合のCTR、視聴維持率、視聴時間、視聴者の国、収益、正確な収益化状態を取得できない。channel.countryは視聴者の国ではなく、検索のregionCodeも米国視聴者を抽出する指定ではない。

サムネイル表示数・CTRの自動化を追加するときはReporting APIのReachレポートを確認する。`video_thumbnail_impressions`と`video_thumbnail_impressions_ctr`があり、カードや注釈のCTRとは別。Analytics APIのメトリクス名を推測して実装しない。[S19–S23]

## 9. YouTube APIポリシーへの対応

### 9.1 単純集計と追加分析を分ける

公式ガイドは、APIデータだけを使った単純な加減乗除・平均の許容例を示している。一方、独自チャンネルスコア、収益推定、コンテンツ分類、コメント感情分析などには追加の派生指標ポリシーがある。すべての差分計算を禁止と解釈するのも、どんな独自分析も無条件で可能と解釈するのも避ける。[S17–S18]

実装では、単純集計の許容範囲を確認し、追加条件の受諾・ユースケースの受理など必要な手続きが確認できるまでは、独自スコア・自動分類・長期競合履歴の機能フラグをOFFにする。YouTube公開値と独自計算値を別の列名・画面ラベルにする。

### 9.2 保存期限

通常の公開APIデータは、統計の履歴と現在のメタデータを区別して30日ルールを実装する。タイトル・説明・コメント本文等は30日以内の更新または削除を管理する。現在値を再取得したことを理由に、過去日時のスナップショットの取得日を更新して保存し続けない。

追加分析のユースケースが受理された場合、一部の統計と派生指標は最大36暦月の保存が可能とされる。他のメタデータまで無期限保存できるわけではない。本人のOAuth認可データには別条件があるため、公開競合データと同じルールにまとめない。[S17–S18]

保存期限は生レスポンス、キャッシュ、抽出済みテーブル、検索索引、バックアップ、LLMへ渡すデータにも適用範囲を確認する。公開コメントの著者情報は本用途では原則保存しない。API制限をスクレイピングや別プロジェクト乱立で回避しない。

| search.list専用 | 100呼び出し／日（各呼び出し1） |
| videos.insert専用 | 100呼び出し／日（各呼び出し1） |
| その他のAPI | 合計10,000ユニット／日 |

元資料の「検索100ユニットを一般10,000ユニットから消費」だけで設計しない。ページ追加も呼び出し数に含む。最終的には実プロジェクトのCloud Consoleの割当を正本とする。日次境界は太平洋時間。

取得規模の例：検索5キーワード×並び順2種類×2ページ=20検索呼び出し。監視50チャンネル・各直近20本=1,000動画なら、channels.list 1回、playlistItems.list 50回、videos.list 20回、コメント20回で一般枠約91ユニット。初期全件探索・追加ページ・再試行は別計上。

リサーチのたびに同じチャンネルの全動画を検索し直さず、uploadsプレイリストとID指定の一括取得を用いる。関連動画サイドバーをそのまま再現することは初期API要件に含めない。[S25]

## 11. 推奨アーキテクチャ（提案）

```
Windows / WSL
└─ Docker Compose
   ├─ web          Nginx等
   ├─ app          PHP / Laravel / 公式Google PHPクライアント
   ├─ worker       Laravel Queue / FFmpeg / ffprobe
   ├─ scheduler    定期取得、期限削除、ジョブ投入
   └─ postgres     メタデータ、制作台帳、ジョブ、実績

非公開ファイル領域
├─ own-source-audio   正規に取得した自作音源
├─ own-images         自作画像・サムネイル
├─ license-evidence   契約・請求書・生成/取得記録
├─ render-output      完成動画とレシピ
└─ youtube-cache      保存期限付き、他の領域と分離
```

PHP/Laravelを主言語とし、Pythonを必須にしない。公式`google/apiclient`を使用する。最初はLaravelのDBキューで開始し、Redisや専用分析基盤は負荷が実測で必要になってから追加する。FFmpegの動画処理はWebリクエスト内で同期実行しない。[S26–S28]

音源・動画の本体はPostgreSQLへ格納せず、ファイルパス、SHA-256、尺、フォーマット、権利情報をDBに持つ。ローカルPCが停止中の定期取得は走らないため、24時間観測が必要になってから常時稼働環境を検討する。自分のPCの実際のレンダリング速度は実測する。

### 初期画面

1. リサーチ一覧：検索条件、チャンネル/動画、元の公開指標、取得日時、サムネイル、根拠付きの本人メモ。
2. 仮説・企画：対象の利用シーン、参考、推測、検証条件、反証、採否。
3. 制作：曲順、音源、画像、タイトル、説明、権利確認、レンダリング状態。
4. 自チャンネル実績：CSV取り込み、動画・期間・流入元ごとの比較、制作費と収益。

### DB・集計の共通ルール

IDは文字列。件数はBIGINT。時刻はTIMESTAMPTZでUTC保存し、UIはJST表示。レポートの日次境界は元ソースのタイムゾーンも保持する。YouTube Analyticsのdayは太平洋時間を基準とするため、JSTの日次スナップショットと無条件に結合しない。[S29]

欠損はNULL。ゼロと分ける。upsertはAPIの現在値に使い、観測履歴は別テーブルに追記する。ただし保存条件の範囲を超えて蓄積しない。複合索引はvideo_id/observed_at、channel_id/observed_at、expires_at、project_idなど。

CSVの粒度を必ず保持する。動画×日次レポートと動画×28日合計レポートを同じ日次行へ入れない。期間合計を日数で均等配分して日次データを捏造しない。重複インポートは冪等にする。後日訂正を反映できるよう取り込み版を保存する。

2026-08-24付の公式チャンネル仕様ではviewCountに全形式の再生開始が含まれるという定義変更がある。集計定義の境界を記録し、公開再生数をそのまま収益対象回数・有効視聴時間とみなさない。[S23]

## 13. 制作ワークフローと品質確認

状態遷移：

```
企画 → 音源選定 → 権利確認 → 構成確定 → レンダリング
     → 全編確認 → 非公開アップロード → Studio確認
     → 予約/公開 → 7日レビュー → 28日レビュー
```

権利が不明、必要なファイルがない、全編確認が未完了の場合は公開準備完了に進めない。音源や構成を変更した場合は確認済み状態を無効化する。

FFmpegでは尺と音声の検査、音量分析、音量調整、曲つなぎ、画像合成、動画書き出しを段階化する。`loudnorm`や`acrossfade`を利用候補にする。ラウドネスの数値をYouTubeの必須規定と誤認せず、対象用途で試聴し内部基準を決める。[S28]

AIで生成した音楽を主に扱う場合、YouTubeのAI利用・合成コンテンツの申告を行う。申告自体で収益化不適格になるわけではない。一方、量産的・反復的で独自の価値に乏しいコンテンツは収益化上の問題になりうる。静止画に波形を加えるだけを対策としない。[S12–S13]

## 14. セキュリティと運用

APIキーをフロントエンド・Git・ログへ出さない。用途別の制限を設定する。OAuth追加時は最小権限とし、refresh tokenは暗号化して保存する。認可解除やデータ削除要求の処理を設ける。

PostgreSQLを無制限に外部公開しない。音源アップロードにはサイズ・拡張子・実体検証を実施する。FFmpegの引数は配列等で扱い、入力文字列をシェル文字列に連結しない。workerにメモリ、同時実行、タイムアウトの上限を設定する。

HTTP 429/5xxは上限付きバックオフ。認証・権限・コメント無効・存在しないIDなどを無限再試行しない。クォータ枯渇時は次の割当まで停止する。ジョブ再実行で動画・統計・費用の重複登録が起きないことをテストする。

自作素材・権利証跡はバックアップする。期限付きAPIキャッシュは別の保存ポリシーに置き、バックアップから復元した古いデータが再表示されないよう期限削除を再適用する。

## 15. 実装順と受入条件

### P0-01 方針・利用条件の確定

内容：初期OAuthなし、用途、予算、音源の商用条件、API派生指標と保存条件、収益化条件の適用日を文書化する。

受入条件：不明な事項が「許可」に丸められず、権利台帳と機能フラグに反映される。年月日で変わる値をコード内へ散在させない。

### P0-02 開発環境とDB

内容：WSL/Docker、PHP/Laravel、Web・DB・worker・scheduler、公式クライアント、設定雛形、最低限の認証を用意する。

受入条件：新規環境で起動・マイグレーション・テストが実行可能。鍵がログに出ない。Web処理と動画処理が独立している。

### P1-01 公開情報の取得

内容：検索条件登録、search→videos/channels、uploads→playlistItems、必要範囲のコメント取得。

受入条件：ページング・重複・欠損・403/429・再試行・クォータ区分をテストする。部分失敗を正常終了に見せない。取得時刻と範囲を表示する。

### P1-02 保存期限とリサーチ画面

内容：現在値と観測履歴を分離し、期限削除、出典表示、参考動画一覧、本人メモを実装する。

受入条件：保存条件を超えたデータがUI/CSV/バックアップ復元経由で残らない。初期機能で独自スコアを勝手に有効化しない。

### P1-03 制作・権利台帳

内容：音源・画像登録、生成条件、契約/証跡、採否、曲順、用途、制作工数を管理する。

受入条件：1動画から全使用素材と利用根拠へ遡れる。未確認音源が公開準備済みにならない。採用率と費用を計算できる。

### P1-04 レンダリング

内容：ffprobe検査、音量分析、曲つなぎ、画像・音声合成、タイムスタンプ作成、非同期ジョブ。

受入条件：同じ入力・レシピを再実行できる。出力尺と曲順が一致。異常な音声・ファイルを失敗として扱い、元データを壊さない。最低1本を人が全編確認する。

### P1-05 手動公開と実績登録

内容：タイトル・説明・曲目一覧の出力、Studio公開チェックリスト、video_idと公開日時の紐付け。

受入条件：ユーザー確認なしで公開されない。AI利用・利用許諾・動画の確認記録が残る。

### P2-01 Studio CSV取り込み

内容：CSVの列と粒度をマッピングし、再取り込み・訂正・期間比較に対応する。

受入条件：取り込み対象のStudio集計と一致する。日次と期間合計を混ぜない。未提供の維持率やCTRを推測で補完しない。

### P2-02 仮説・実験・収支

内容：変更内容、比較期間、評価指標、結果、継続判断、月次費用と収益を保存する。

受入条件：本人の実収益と競合の公開指標を区別。サンプル不足は保留。複数の仮説を試した経緯も残し、当たった結果だけを報告しない。

### P3-01 追加分析の有効化（条件付き）

内容：必要なポリシー手続きと許容範囲確認後に、独自比率・分類・保存期間の拡張を行う。

受入条件：受理/受諾根拠と適用日を記録。元のYouTube指標と独自指標を明確に表示。承認の失効や条件変更に対応可能。

### P3-02 OAuthによる自チャンネル分析（方針変更時）

内容：Analytics、Reporting、必要ならData APIのアップロードを追加する。OAuthなし要件と同時に満たせるとは扱わない。

受入条件：必要スコープを限定。解除時の削除。ReachのCTRと別種のCTRを混同しない。予約公開でも最終の人間承認を残す。

### P3-03 音楽生成API（別契約確認後）

内容：公式APIを持つ採用サービスのadapterを追加する。

受入条件：WebサブスクとAPI料金を混同しない。予算上限・日次生成上限・冪等キー・失敗時の課金記録を持つ。非公式APIやDL制限回避を含めない。

## 16. 最初の完成形

「20前後の競合を比較できる」「1本のBGM動画を許諾付き素材から制作できる」「公開後の反応と費用を記録できる」を最初の完成条件とする。リサーチだけ、または自動投稿だけが完成しても事業仮説を検証できる状態とはみなさない。

この設計書は実装用のたたき台であり、公開チャンネル、APIプロジェクト、サービス契約、音源の採用結果を確認したうえで、各P0/P1タスクをIssueへ分割できる。
