# 取得・分析・削除のライフサイクル

> 文書ID：LMA-002  
> 状態：追加実装仕様。コマンド名は実装予定のインターフェース。  
> 整理日：2026-10-14  
> 読む場面：バッチ、状態管理、ディレクトリ、削除、再開を実装するとき。

## 1. 入力と許諾

入力は1件ずつのJSONマニフェスト。必須情報は `job_id`（UUID）、`input_kind`（youtube_url/local_file）、`input_value`、`subject_type`（own/competitor）、`mode`（audio/audio_visual）、`profile_id`、作成日時、利用根拠の参照ID、取得・分析・Codex送信それぞれの確認状態。用途やタイトル等は別の参考データ欄とし、作業命令として解釈しない。

URLだけを承認済みと扱わない。ネットワーク取得前に `acquisition_approved`、分析前に `analysis_approved`、考察前に `derived_text_to_codex_approved` を確認する。画像を渡す場合は `images_to_codex_approved` も必要。未確認なら停止し、モデルが承認状態を補完してはならない。

YouTubeの公開URLは技術的な入口であって、取得・自動アクセスの許可ではない。サービス側と権利者側の適用条件を確認する。自分の元ファイル、公式に取得した自作動画、権利者から受け取った許諾済みファイルも同じ分析入口で扱う。[出典](sources.md)

## 2. ディレクトリ

全体をGit管理・クラウド同期・通常のバックアップから除外する。WSL内の同一ファイルシステム上に、専用ルート `var/local-analysis/` を作る案とする。Webの公開ディレクトリには置かない。

```text
var/local-analysis/
  requests/                 # 入力マニフェスト。音源は置かない
  jobs/                     # 状態・ロック情報・期限・削除記録。秘密情報は除外
  tmp/downloading/<job_id>/  # 取得途中、.part、結合前ファイル
  downloads/<job_id>/        # 検証済み・未処理のREADYだけ
  work/<job_id>/             # 処理中、再試行待ち、抽出音声・フレーム
  results/.staging/<run_id>/ # 未確定結果。DB取込の対象外
  results/<run_id>/          # 確定した分析結果。音源・画像は置かない
```

`downloads` が利用者のいうDLディレクトリ。完成・検証前のファイル、分析中ファイル、失敗ファイルをここに残さない。任意ファイルの直接放り込みは禁止し、登録コマンド経由で検証する。

自作素材の原本はこのルートの外で保存する。`local_file` は原本を通常のコピーで取り込む。移動・symlink・hardlinkで代用しない。以後の削除対象は管理下のコピーだけで、原本は変更も削除もしない。

## 3. 状態遷移

```text
REQUESTED → DOWNLOADING → READY → ANALYZING → RESULT_COMMITTED
                                                    ↓
                                               CLEANUP_PENDING → DONE
```

失敗時は `DOWNLOAD_FAILED` / `ANALYSIS_FAILED` / `VALIDATION_FAILED` / `CLEANUP_FAILED` を区別する。待機中の期限切れは `EXPIRED`。DB取込状態は別に `not_imported/imported/import_failed` とし、素材削除をDBの稼働状態へ依存させない。

- `REQUESTED`：許諾、URL/パス、設定、ディスク容量、同じ依頼の処理済み状態を検査。
- `DOWNLOADING`：一時領域へ取得。取得終了コードだけでREADYにしない。
- `READY`：ファイル実体、サイズ、音声ストリーム、尺、ハッシュ、マニフェストの整合確認後、ジョブディレクトリをatomic renameでdownloadsへ公開。
- `ANALYZING`：排他ロック取得後にdownloads→workへatomic renameして占有。1件ずつ処理する。
- `RESULT_COMMITTED`：後述の確定処理を完了した状態。AIが「終わった」と書いただけでは到達しない。
- `DONE`：一時素材が実際になく、削除記録が保存された状態。

状態ファイルとrenameの間で停止しても、ルート配下の配置、確定マーカー、ハッシュを照合して復旧できるようにする。mtimeだけを真実としない。

## 4. yt-dlpバッチ

公式yt-dlpの `home/temp` 出力先を使い分けられる。ただし本システムは追加検証後にのみdownloadsへ公開する。[出典](sources.md)

実装要件：

- URLの許可形式はHTTPSの単一YouTube動画URL（youtube.com/watch、youtu.be等）をパースして正規化する。チャンネル・プレイリスト・live/upcoming・任意ホストは初回対象外。URL中にlistがあっても単一動画のみ。
- プロセスは引数配列で起動。`shell=True`、文字列のシェル連結、ユーザー指定の任意yt-dlpオプションは不可。ファイル名はタイトルではなく内部IDから作る。
- `--ignore-config` 等で利用者環境の隠れた既定設定を読み込まず、採用版・依存ツール・実引数を機密情報なしで記録する。実際のオプションは採用版で確認する。
- audioは取得した圧縮音声をそのまま保存し、無意味なMP3再エンコードをしない。audio_visualは映像解像度上限を持ち、音声付きか確認する。小さい形式がないとき勝手に高画質へ切り替えない。
- 障害時のリトライ回数、転送量、ディスク容量、尺、実行時間を制限する。長さを確認できない素材は保留。上限超過を勝手な切り詰め成功にしない。
- 初期設定案：同時処理1件、READY最大2件、1素材最大2 GiB、最大尺2時間。作業領域にはデコード等の追加容量も見積もる。これらは費用・容量対策の提案値で、分析の正解ではない。設定変更履歴を残す。
- 音声や画像に加え、.part、分割ストリーム、変換途中ファイル、yt-dlpキャッシュ等をすべてジョブ管理領域内へ限定する。
- Cookies、ログイン情報、署名付き配信URL、全info.jsonを結果・Git・Codexのプロンプトへ送らない。初回はCookiesを必要とする経路を対象外にする。
- DRM、地域・会員・年齢・認証制限、bot判定等の回避は実装しない。取得できない場合はエラーとして返す。

URLの再取得は同じバイト列を保証しない。取得日時、動画ID、選択形式、codec、実ファイルSHA-256を記録する。取得履歴と分析完了履歴は別物。yt-dlpのdownload archiveだけで分析済みと判定しない。

## 5. 結果確定と削除

1. 計測パックを作りハッシュを固定。Codexは考察部分だけを書き、計測値を編集しない。
2. finalizeが計測パックと考察を検証・統合し、`analysis.json / features.csv / report.md` をstagingへ出力する。
3. JSON Schemaに加え、証拠参照、区間、必須計測の完了、元計測パックとの一致を検査する。
4. 3ファイルのサイズとSHA-256を `bundle.json` に記録。書き込みをflushし、可能な環境ではfsync後、ファイルを再読込して照合する。
5. stagingのディレクトリを `results/<run_id>` へatomic renameして公開し、確定状態を保存する。既存の異なる結果を上書きしない。
6. `CLEANUP_PENDING` を永続化し、対象ジョブが所有する一時素材・音声・フレーム・サムネイル・.part・中間コピーを削除する。
7. ファイル不在を検証し、`jobs` に `deleted_at / cleanup_status / 削除対象件数` を保存してDONEにする。

確定結果のハッシュを削除記録のために後から書き換えない。DBが停止していても工程6へ進める。DB再取込は保存済みJSONから行い、素材を再DLしない。

結果の保存・検証に失敗したら成功時削除は行わない。workに隔離し、期限内に再試行する。削除だけ失敗したときは分析を繰り返さず、cleanupのみ再実行する。

## 6. 失敗・停止時も素材をためない

初期案は、未完了素材の最大保管24時間（最初に管理領域へ取り込んだ時刻から）。再試行やフォルダー移動で期限を延長しない。READYにも適用する。短い契約期限があればそちらを優先する。

期限切れでは、最小限のエラー・未完了記録を保存して一時素材を削除しEXPIREDにする。分析結果が完成したことにはしない。再試行には明示した再取得が必要。

cleanupは各操作の開始時と終了時に呼び出し、稼働中の定期実行にも使える独立コマンドにする。PC停止中の期限到来やプロセス強制終了時に、即座に削除されたと保証しない。次回起動時は分析・取得より先に復旧と期限処理をする。

ロック中の生存プロセスを別cleanupが削除しない。全体実行時間の上限と子プロセス終了を扱い、異常停止後のロック回収をテストする。

## 7. 削除の安全条件

削除関数はjob_idだけを受け、任意の削除パスをモデル・JSONから受け取らない。専用ルートに作成済みの識別マーカーと、ジョブ所有マニフェストを必須にする。

正規化後のパスが専用ルート内であることを確認し、symlink・hardlink・親参照・ルート自身・ホーム・Gitルート・別ジョブ・外部原本への到達を拒否する。`rm -rf downloads/*` 等の一括ワイルドカード削除は禁止。対象を限定したdry-runを用意する。

通常の削除はSSDの物理消去、バックアップ、Codex側に送ったデータ、会話履歴からの完全消去まで保証しない。生素材・フレームはバックアップや会話添付に残さない運用を基本とする。
