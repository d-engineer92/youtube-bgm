# 探索語を増やす方法・Codex向け固定依頼

> 文書ID：EXP-005  
> 状態：追加実装仕様（未実装）／2026-10-14  
> 読む場面：辞書更新・候補JSON取込・別の切り口の表示。

## 目的

利用者が最初から英語のジャンル名や用途語を知っていることを要求しない。同梱のprimaryで開始し、related候補を意味付きボタンで深掘りできる。カタログは固定の正解ではなく、独立に更新する検索仮説集。

**辞書だけで未知の流行を自動検知する機能ではない。** 未知の語を広げるときは、Codexに新しい候補を提案させ、人が採用してから検索する。一般知識からの提案を、現在の流行を観測した事実と書かない。

今回、API本文からの自動タグ抽出・分類、検索サジェストのスクレイピング、AIの無制限再帰探索は実装しない。候補案にAPI由来の情報を渡す処理も作らない。取得済みの原題・数値を外部AIへ送れば許容されると仮定しない。

## 二つの更新経路

1. 開発時：正本カタログを版更新してレビューする。実装時はruntime configへ一度移し、docs側を参照に置き換える。同一辞書の二重メンテナンスをしない。
2. 利用時：本人/Codexの候補JSONを検証・プレビュー・明示適用し、exploration_keywordsへproposedで保存する。承認操作後にだけ検索可能。インポート自体ではAPIを呼ばない。

related候補は事前にレビューした同梱仮説なので、利用者がボタンを押した場合はその1語を実行可能。JSON提案は未承認のまま自動実行しない。関連候補の既存テーマとの所属は探索の整理用であり、返った動画の内容分類ではない。

## 固定プロンプト：keyword-proposal-v1

```text
あなたの役割は、BGMの次の検索候補を作ることです。
入力は探索プリセット、既存の検索語一覧、日本語の調査目的だけです。
YouTube APIの本文・数値・コメントや、未提供の音声を分析したと装わないでください。
有料API、ダウンロード、ブラウザー操作、DB更新、検索実行は行わないでください。

既存語と重複しない候補を最大8件、下記のJSON形式だけで返してください。
用途、場面、音楽の方向、時間帯のうち複数の切り口を含めてください。
各語の日本語での意味と、なぜ調べる価値があると考えるかを記載してください。
「今人気」「高単価」「確実に伸びる」等の未確認の主張は書かないでください。
特定のアーティスト・作品のコピーや、医療効果を保証する語を推奨しないでください。
新しい切り口はparent_theme_id=nullで構いません。
これは需要未検証の探索仮説であることを固定フィールドで示してください。
```

## 入出力契約

UTF-8、schema_version=1.0.0。最大ファイルサイズ64 KiB、最大8件、未知キー拒否。入力ファイルはローカルの非公開領域で扱う。画面の一般ファイルアップロードは不要。Artisanコマンドのdry-runとapplyを用意し、実装時READMEに実際のコマンドを記載する。

```json
{
  "schema_version": "1.0.0",
  "prompt_id": "keyword-proposal-v1",
  "source_kind": "codex_proposal",
  "preset_id": "en-US",
  "demand_status": "unverified",
  "candidates": [
    {
      "id": "7d8925aa-7db6-4ea6-b73d-74e0e1015431",
      "parent_theme_id": "focus",
      "label_ja": "画面作業の集中時間",
      "query": "instrumental music for deep work",
      "meaning_ja": "深く集中する作業向けの歌詞なし音楽を探す言い方",
      "reason_ja": "広い集中用途から、作業の場面を絞って比較するため"
    }
  ]
}
```

例は未実行の書式例。モデルIDをJSONの自己申告で確定しない。入力条件・プロンプト版・取込時刻はバッチ側で記録する。

preset_idはen-US/ja-JP、source_kindはcodex_proposal/manual、parent_theme_idはカタログIDまたはNULL。NULLなら新しい探索テーマの候補として日本語名を表示できる。候補IDはUUID、queryは1〜120文字、label_jaは1〜80文字、meaning/reasonは各1〜500文字。文字列以外、制御文字、重複ID、未知プリセット、禁止された追加フィールドを拒否する。

同じpresetのqueryをNFKC・空白正規化・英字大小統一したキーで重複検出する。原文queryは別途保持。既存候補と同語なら二重作成せず、既存の承認状態も変更しない。同一UUIDで異なる内容は競合エラーとする。HTML/Markdownを実行・未エスケープ表示しない。JSON内文字列をシェル・SQL・コマンド引数名として実行しない。

## 検証

Codex応答をそのまま信用せず、PHP側で構造・列挙・長さ・重複・禁止フィールドを検査する。dry-runはDBを変えず、追加/重複/拒否を示す。applyは1トランザクション、失敗は全体を戻す。取込後の承認/保留/無効化により、次回の候補表示を制御する。

流行の根拠は提案文ではなく、実際の取得結果を見て別途検討する。収益が出た後の有料AI導入や自動分類は別仕様とする。
