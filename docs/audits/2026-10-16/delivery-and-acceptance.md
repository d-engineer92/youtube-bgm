# 手戻りを減らす実装順と、利用成果の受入条件

> 文書ID：AUD-005 / 監査日：2026-10-16  
> 状態：監査に基づく次の作業提案。DB消去や追加機能の実行記録ではない。

## 1. 最初に正本を揃える

PR #6を別システムとしてもう一つ実装しない。変更中のコード・ブランチ・未コミット作業を確認し、AUD-002/003の対応を既存TRK/EXP/FTR/RES/POLの正本へ反映する。「実装済み」と「仕様に書いた」も区別する。

最初の設計出力は次の4つで足りる。

1. 原資料の項目 → 見る画面／入力 → 必要データ → 処理 → 判断に使う出力 → 受入確認の対応表。
2. 対象・検索・観測・メタデータ証跡・分析・企画のデータ契約。
3. 一覧→横断選択→比較→仮説→試作下書きの画面遷移と状態表。
4. 今回の切替で完成させる範囲、手動で補う範囲、条件付き機能、後回しの範囲。

新着削減、最低再生数足切り、追跡の7日終了は復活させない。既に承認された一回限りの旧調査データ消去を、今後の通常マイグレーションへ組み込まない。

## 2. 実装は二段階。ただし完成条件は一本の流れで定める

### 段階A：収集し直す前に完成するもの

TRKの全動画・関連チャンネル追跡、必要な観測項目、メタデータ版、検索所属との独立、同じ期間計算、期限・権利の機能境界、予算と稼働確認、一覧の変化表示と横断選択、既存投稿一覧取得の範囲・再開の維持、リセットと世代保護を実装・検証する。

後から取り返せない情報を先に揃える。分析画面の外観が全部完成していないことを理由に履歴収集を永遠に待たせないが、保存するデータと出力参照の契約が未定のまま消去しない。

### 段階B：初心者が分析できると呼ぶ前に完成するもの

既存RES-001の最小の質問・観察・仮説・反例・次の確認を比較画面に実装し、FTR-003の一枚の制作指示書へつなぐ。チャンネルの直近投稿の確認範囲と、注目対象の新規投稿発見の操作を整える。自作の振り返りは手入力でよい。

AIへ渡すことを採用する場合は、期限・送信範囲・利用条件を確認し、固定パックとプロンプト版、結果の根拠確認を一巡させる。追加条件が未確認の機能は無効と明示し、基本の公開数値表示・許可範囲の計算まで止めない。高度な分類のために有料APIを増やさない。

段階Bは低コストの既存予定機能の接続であり、自動生成・自動投稿・会計や実験基盤の全面構築ではない。段階Aのデータ契約へ追加で載せ、原則DBを再リセットしない。

## 3. 一回限りのDB切替ゲート

TRK-004の対象DB確認、worker/scheduler/API停止、旧ジョブの書き戻し防止、dry-run、調査データ全消去、API消費台帳保護を維持する。

消去前に、A-01〜07・A-10のP0が「対応済み」または明示された条件付き無効になり、下記のG01〜G09が専用PostgreSQLで通ること。実際の翌日観測は新収集後なので、未確認としたまま別の完了項目に残す。監査用ダンプを勝手に保存して旧APIデータの期限を延長しない。

コードのリリース・PR統合・通常DB操作の権限は、利用者の依頼と環境に従う。本監査PRの存在を、追加の自動マージや再リセットの承認と扱わない。

G02〜G09は人工fixtureで時間を進めた検証と、実時間の検証を別に記録する。実24時間の成功は、正常DBに本当に2点目が追加された後でだけ報告する。G10は「横はみ出しなし」だけでなく、対象を見つける操作数、元画面への復帰、スマホでの二対象の見比べやすさを確認する。
