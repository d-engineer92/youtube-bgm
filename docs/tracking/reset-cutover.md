# 旧調査データ全消去と新方式への切替

> 文書ID：TRK-004  
> 状態：2026-10-16に利用者が「今のレコードはすべて削除」「改修と同時にDBを空に」と指示。実行は未実施。  
> 実行者：対象ローカル環境へアクセスできるCodex。ChatGPT側ではDB操作していない。  
> 対象：このyoutube-bgmプロジェクトの通常DB `youtube_bgm` の調査データ。

## 1. リセットの意味と範囲

旧データを選別して移行したり、後付けでウォッチを有効にして引き継いだりしない。旧調査データを全消去し、新方式の初回実取得から揃える。過去の欠測が数学的に無価値という一般論ではなく、今回は利用者の再開始方針に従う。

| 消去するもの | 扱い |
|---|---|
| 動画・チャンネル・対象ID・観測履歴 | 全件。live/demoの両方 |
| 検索/探索run・task・順位・所属・ページトークン | 全件 |
| 比較と目的メモ、手動ウォッチ | 全件。参照があることを理由に旧データを残さない |
| 個人が取り込んだ候補語・承認状態 | 全件。同梱設定カタログは残す |
| 旧データ用のキュー・失敗ジョブ・セッション・キャッシュ | このプロジェクトのものを全消去 |
| 改修で追加する追跡/スナップショット/分析転記 | 旧世代があれば全消去 |
| アプリ管理下に存在する旧時系列出力 | 同じ世代のJSON/CSV等を消去。管理外パスへ探索削除しない |

構造を再構築する目的ではない。DBスキーマ・インデックス・migration履歴・コード・同梱カタログ・`.env`・APIキー・APP_KEY・認証情報・役割/権限は保護する。ローカル音源分析の原本/結果はこのSQLデータ消去の対象外。別プロジェクト・別DB・Google/YouTube上のデータは触らない。

**API消費台帳だけは調査データではないため保護する。** 既に消費した当日のsearch/readやblocked状態は、リセットで復活しない。`api_days` の必要な稼働記録を維持し、UI上も同じ使用量を示す。migration・API予算・新世代等の稼働行を残すことを報告し、「DBの全テーブルが文字通り0行」とは言わない。「調査データ0件」を確認する。

## 2. 消す前の必須条件

- 新追跡処理、画面、復旧、リセットのテストが専用PostgreSQLテストDBで成功している。
- 実装の切替対象コミットを特定し、未コミットの作業を失わない。PRの自動マージを承認されたと解釈しない。
- 通常環境のAPI受付・worker・schedulerを停止し、実行中プロセスがなく、旧ジョブが書き戻せない状態にする。queue:restartの呼出だけで停止済みと判定しない。
- 実効接続のPDOドライバー、current_database、current_user、接続ホスト/ポート、Composeプロジェクト/サービス、対象テーブルを読み取り確認する。
- このリポジトリに対応するローカルComposeのDBかつ `youtube_bgm` だけを許可。`postgres`・template DB・他アプリDB・リモート接続・不明な接続先を拒否する。DB名一致だけで許可しない。
- 手順のdry-runで削除予定テーブルと件数、保存する運用テーブル、世代IDを表示する。公開ログへキー・タイトル・外部ID・メモ本文を出さない。

現在のテーブルを列挙してリセット対象を明示する。初期候補は `comparison_target,comparisons,observations,videos,channels,run_items,fetch_runs,targets,exploration_tasks,explorations,exploration_keywords,jobs,failed_jobs,job_batches,sessions,cache,cache_locks` と改修で追加する調査用テーブル。存在/非存在とFKを確認し、未分類テーブルがある場合は停止して報告する。

## 3. 一回限りの専用実行

リセットは専用の保守コマンド/手順とし、通常migration、composer install、Web起動、scheduler、通常テストに混ぜない。実行オプションとして対象DB名・現世代・破壊操作承認を明示させ、既存の利用者承認をこの切替で使用する。追加の会話で承認を取り直すために作業を止める必要はないが、技術的な照合は省略しない。

DBロックとメンテナンス状態の下で対象テーブルをトランザクションで消去する。FKに応じて順序付きDELETE/明示TRUNCATEを選ぶ。未知のテーブルまで巻き込むCASCADE、DROP DATABASE、`migrate:fresh`、`docker compose down -v`、ホスト全体のファイル削除は使わない。

旧ジョブが再配信されても新データへ作用しないよう、リセット世代をUUIDで更新し、全収集・追跡ジョブと再開要求で世代を照合する。IDの再利用だけで旧ジョブが新レコードに当たらないこと。リセットコマンドの再実行は同じ操作IDなら二度消去せず、新データを消さない。

アプリ管理下の旧出力がある場合、対象世代/許可パスの検査後に除去する。DB消去成功・ファイル消去失敗を区別し、同じリセットをDB側まで繰り返さない。新機能の結果以外の既存音源分析ファイルを削除しない。

今回の旧調査データを残すための自動バックアップやarchiveコピーは作らない。既存の管理外バックアップの有無は分かる範囲を報告し、勝手に外部ストレージを削除しない。

## 4. 空の状態を確認してから新規収集

1. 消去対象が0件、API使用量/blockedが不変、キー/設定/スキーマが保護されていることを確認する。
2. 新世代を有効化し、Web/worker/schedulerを新コードで起動。追跡対象0件・旧ジョブ0件・heartbeat正常を確認する。
3. 残っている実API予算内で、既定US/enの初回探索を一度だけ開始する。16検索ページは維持し、枠が足りなければ既存の途中保存・再開を使う。
4. 新しく取得した動画に初回実測と次回予定がすべて揃うことを、手動ウォッチ未登録のまま確認する。最初から再生数がある動画に0を捏造しない。
5. 旧データは再投入しない。検索で同じYouTube IDが再発見されることは正常であり、新方式での新しい初回観測として扱う。
6. 次の実際の予定時刻到来後、手動登録なしで2点目が保存されることを確認する。時計を進めたテストは実24時間観測とは区別する。

## 5. 完了報告

実装/テスト/リセット/新規取得/実翌日観測を分ける。通常DBリセットの実施日時、対象DBと世代、削除テーブル別件数、保護したAPI台帳の前後、空確認、新規追跡数、次回予定、停止/未確認事項を示す。実データの本文・キーはGitへ載せない。

環境の接続先を確認できない場合はそこで止め、消去済みと報告しない。実装前に現在のDBだけを先に空にしてはならない。
