# 文書の分割・参照・更新ルール

> 整理日：2026-10-14

## 分ける単位

「一つの機能を実装する」「一つの判断を行う」ために、まとめて読む内容を一つの文書にする。画面、外部API、数値の定義、保存期限、受入条件を分ける。カラム一つ・質問一つごとのファイルにはしない。

初期の技術・データ案は短いため一つに置く。物理スキーマなど独立して変更する詳細が増えたら分割する。行数だけで機械的に分割しない。

## 入口と読み方

ルートのAGENTS.mdは共通の作業案内だけ。docs/README.mdは一覧・作業別の参照先だけ。具体的な実装仕様は、それぞれの文書を正本にする。

入口 → 作業に該当する文書 → 明示された依存文書、の順に読む。全ファイルを毎回連結する運用にはしない。ただしAPI保存など共通の安全条件は、対象作業で省略しない。

これは読み方の設計であり、分割しただけで全AIが必ず最適な取得をするという保証ではない。

| 内容 | 正本 |

| 何を作る／作らない | [初回実装の範囲](../project/mvp-scope.md) |
| 画面の操作・入力・表示 | [機能別仕様の入口](../README.md) |

別の文書では関連項目へリンクし、同じ仕様全文を再掲しない。受入条件は仕様を検証する観点であり、新たな機能を増やす場所ではない。

## 文書冒頭に持つ情報

文書ID、状態、読む場面、整理日、元資料または決定根拠を記す。「提案」「採用済み方針」「実装済み」「外部確認済み」は区別する。根拠がない項目を自動で確認済みにしない。

外部仕様に依存する内容は、公式URL・確認日・適用範囲・未確認点を残す。記事の個人事例、利用者の仮説、プロジェクトの設計判断を混ぜない。

## 変更時

1. 関係する正本を更新する。初回の対象範囲が変わるなら、先に利用者の方針変更を確認する。
2. 受入条件と、関連リンク・作業別参照表への影響を確認する。
3. 大きな方針変更は`docs/decisions/`へ理由と影響を記す。
4. PRには読んだ文書ID、変更した文書、実装済み・実データ確認済み・未確認・意図的に未実装を区別して書く。

日付だけ新しくして未確認情報を更新済みにしない。旧版は通常の実装対象に戻さない。原文訂正が必要な場合も、履歴保全の原本を黙って書き換えず、現行文書と変更理由を更新する。
