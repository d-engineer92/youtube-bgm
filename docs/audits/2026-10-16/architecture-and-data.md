# 設計上の欠落と、切替前に固定する境界

> 文書ID：AUD-003 / 監査日：2026-10-16  
> 状態：監査提案。PR #6と各正本へ調整して採用する。  
> P0＝新方式のデータ収集・一回の消去に先立って解決／仕様確定。P1＝初心者向け分析の完成を宣言する前。P2＝後続の明示的拡張。

## A-01 / P0：全動画追跡の方向は正しい。取得成功を利用成果と分ける

現行Collector::refreshWatch()はwatched=trueだけ。PR #6/TRK-002は、全取得経路の初回保存と追跡登録、約24時間ごとの観測、チャンネル統計、稼働表示まで規定しており、この修正は維持する。低再生を削除する案へ戻さない。

資料の目的は「何本取れたか」ではなく、昨日0回の動画が今日どの程度増え、増えなかった動画と何を比較するか。取得・解析・判断を別の完了状態にする。

## A-02 / P0：将来の分析に必要な観測項目とメタデータ版が不足

現行store()は動画のview/like/commentを現在値へ保存するが、observationsはviewとsubscriberのみ。チャンネルvideo_countも現在値のみ。タイトル・サムネイルURLを上書きし、説明・タグは保存しない。TRKの「他公開数値」は抽象的で、何を残すか確定していない。

切替時に、少なくとも次の項目の採用・用途・欠損理由・期限を確定する。

- 動画のview_count / like_count / comment_count、チャンネルのview_count / subscriber_count / video_count。非公開や無値はNULL、0と区別。登録者の丸めを保存・表示する。
- 動画のタイトル、必要な説明・タグ、公開日時、尺、配信状態、返却される言語・カテゴリ等。チャンネルの説明やキーワードは比較用途と取得可能性を確認して追加範囲を決める。APIが返さないものを補完しない。
- 観測時点のメタデータ版参照、取得時刻、内容ハッシュ、独立した期限。変化した項目を検出して版を追加し、過去版を「現在」として表示しない。履歴の書換えはしない。
- サムネイルURLが同じでも画像内容が同じとは保証しない。画像の実保存・ハッシュ採取は許諾と期限を明確にした別の証跡処理。初期に全画像を無条件保存しない。証跡がない時期の構図・色は未確認。

S1 L1934–1939の「変化のきっかけを時系列で追う」には数値だけでは足りない。必要な生データを後で追加しても、過去分は復元できないため、画面装飾より先に決める。

## A-03 / P0で契約確定・P1で導線：既知動画の更新と、新しい投稿の発見は別

PR #6には関連チャンネルの統計更新があるため「チャンネル追跡が全くない」とは評価しない。一方、既知動画とチャンネル数値だけ更新しても、翌日そのチャンネルが出した未登録動画は増えない。

現行には手動でウォッチしたチャンネルのuploads一覧を一部更新する処理がある。これを新追跡で黙って消さない。次の役割を分離する。

1. 全取得済み動画と関連チャンネルの公開数値更新（自動・お気に入り不要）。
2. 新規候補の検索（EXP。実行日・検索語・範囲を残す。毎日自動検索する約束を勝手に増やさない）。
3. 利用者が注目対象として選んだチャンネルの新規投稿確認（uploads、予算内、未走査部分と再開位置を保持）。選択は新たな発見の範囲を絞るためで、既存動画の追跡条件ではない。

「直近5〜10本」には、取得済みの任意5本ではなく確認範囲・確認日時・未取得を付ける。公開動画数の純増は投稿数と同義ではない。最古の確認動画は本当の初投稿と断定しない。チャンネル総再生数は全形式を含み、収集した長尺BGMの合計とは別。

## A-04 / P0：観測間隔・公開後経過・比較基準を一つの計算契約にする

現行比較はPresentation::delta()の最新2点、探索カードはdailyDelta()の24時間以上離れた点。短い手動更新を挟んだ場合や予定時刻の揺れで、同じ動画でも異なる差分が見える。TRKの約24時間という方針に加え、共通の基準点選択を明文化する。

- published_at、first_seen_at、scheduled_for、observed_at、区間start/end、基準as_ofを別項目にする。日付の表示だけで時刻を失わせない。
- 生の増分＝v1−v0と実時間を必ず組にする。0分母の率はNULL。負の差分、取得失敗、0増分は別。
- 24時間未満の直近2点、24時間以上離れた点、複数日を跨ぐ区間を区別し、48時間の増分を24時間の増分順へ混ぜない。
- 「約24時間」と呼ぶ許容幅や欠測時の選び方は設定・テストで固定する。時刻の揺れのために不要な48時間点を選ばない。補間して過去の再生数を生成しない。
- 加速の比較は少なくとも連続2区間の実データと比較可能性を要する。3点あるだけで原因を証明しない。
- 日次換算を使う場合は実測値と分離し、方法・対象範囲を表示する。初期は無理に一つのランキングへ混ぜず比較できない群を分けてもよい。
- 保存した比較は対象IDだけでなく、期間・基準時刻・用いた観測ID・並び順を固定。最新値を見る操作とは分離する。期限後は根拠失効を示す。

## A-05 / P0：永続対象・観測・検索所属・分析結果を分離

物理名やテーブル数を増やすことが目的ではない。次の責務と関係を、既存PostgreSQL内で確定する。

| 責務 | 維持する情報と境界 |
|---|---|
| 対象と追跡 | dataset/source/video(or channel)ID、本人宣言のown/competitor/unknown、開始・停止・次回。宣言だけでAPI認可扱いにしない |
| 検索所属 | query/theme/lens/preset、検索日時、順位、カタログ版、取得範囲、期限。同じ動画が複数経路を持つ |
| 観測 | 予定枠・実時刻・数値・欠損状態・由来・期限。検索runの削除で期限内の観測がcascade消去されない |
| メタデータ／証跡 | 対象と時点、版、ハッシュ、取得・送信の利用範囲、独立した期限。画像URLだけを見たことにしない |
| 比較・分析 | 選択対象、基準点、問い、事実参照、仮説、反例、未知、承認状態、プロンプト・モデル・Schemaの版 |
| 自分の企画・試作 | 利用場面、参考にする要素、変える一要素、費用・時間・許諾・公開後確認。APIの期限付き根拠とは分ける |

初期検索テーマは動画の実ジャンルではない。本人の解釈ラベルもYouTube公式カテゴリと別にし、独自分類機能の利用条件を先に確認する。US/JPは別検索条件であり、同じ動画の公開数値を国別に複製・解釈しない。

## A-06 / P0：28日履歴で可能な判断と、長期目的の未達を明示

TRKは追跡を続けつつ履歴28日ローリングとする。S1の1〜2か月、何か月・何年も継続、S3の3〜4か月季節窓は、このままでは完全に検証できない。古い動画が「今も増えるか」は観測可能だが、過去数年ずっと増えたことの証明ではない。

公式追加ポリシーの適用・用途の受理を確認すれば統計等の保存拡張の可能性がある。未確認の現在は有効化しない。設定は統計・メタデータ・証跡・API由来分析の種類ごとに期限と許諾状態を持たせる。承認番号等がないのに設定値を365へ変更する運用は禁止。ファイル化・手書き化で迂回しない。

追跡開始、初回の数値、月間差分を別扱いにする。28日が過ぎたら初回値は期限外となる。APIの数値を保存した自己メモも自動的に永久の独自ノウハウへ変わるわけではない。

## A-07 / P0：増え続ける追跡対象と稼働予算を見積もる

TRKの追跡優先は維持。動画・チャンネルの50ID単位取得の概算はceil(Nv/50)+ceil(Nc/50)だが、異なる期限群・再試行・新規詳細・uploads確認で増える。実測リクエスト数で確認する。20検索/500readはアプリ側の運用設定であり、公式のサービス限界ではない。

追跡と新規発見の予算を分離しながら共有台帳で予約する。収集済み低再生動画の勝手な脱落ではなく、新規発見の受付待ちで容量不足を見えるようにする。全候補の追跡が何か月後も無制限に無料とは約束しない。稼働heartbeat、遅延数、最古の期限到来を表示する。

## A-08 / P1：分析と判断軸Bへの橋が未実装

comparison.blade.phpは比較目的の保存だけ。RES-001とFTR-003は文書のみ。TRK-003は最大6件の時系列出力と文章プロンプトを規定するが、事実→仮説→反例→試作の構造化保存と、AI結果の受取確認はない。

最小実装は既存比較画面のガイド入力と一枚の制作指示書で足りる。無料記述の空欄だけ、またはAIの長い文章だけで完了にしない。AIを使わなくても下書き保存できること。AI出力は根拠の対象・観測・メタデータ版を参照し、検証して本人が採用／保留する。音源計測結果の全DB取り込み（LA-3）は後回しでも、run_id/hash/対象区間を後で紐付けられる形式は今決める。

## A-09 / P1：音源計測と音楽理解・画像観察を混同しない

profile-v1.jsonはRMS、無音、ラウドネス、ピーク、フレーム等。音を直接理解するモデルの実行、BPM、キー、楽器の正解を検証したものではない。抽出フレームは動画の背景であり、検索に表示されるサムネイルそのものでもない。

人の試聴と計測を併用し、S1の冒頭の楽器・テンポ・雰囲気・使用楽器を、確信がなければ未確認のまま記録する。後から必要なDSPを追加してよいが、有料モデルや全曲の高度解析を今の必須にしない。ファイルを削除する前に、必要な計測結果・確認時刻・証跡の参照が保存されていることを検査する。

## A-10 / P0で利用境界・P1で操作：API／AI／素材利用の確認を表示に反映

現行layoutはYouTubeトップへのリンクと一般的注意だけで、API利用規約・プライバシー説明の導線を確認できない。公式の最低条件に照らして、最小の説明ページと必要な同意導線を補う。認証基盤全体を新設する意味ではない。

単純な数値計算と、追加の独自分類・感情分析・長期統計の扱いは分ける。追加条件の未承認を「Codexへ手動で渡すなら問題なし」としない。提供記事のAI活用例自体も許諾の証拠ではない。

APIクライアントのYouTube映像音声の取得にはYouTube側の制限がある。素材の権利者の許可、取得手段の許可、Codexへ送る許可は別。チェック欄だけで取得権限を作らない。許諾済みの手元ファイルでの解析経路は独立して使える。

## A-11 / P1は手動・P2は自動：自分の動画の改善ループ

自作の動画を対象として区別する（ユーザー宣言と権利・API認可は別）。競合の公開指標と、本人がStudioで見たCTR／平均視聴時間／維持率／流入元／RPMを一つの数値へ混ぜない。本人指標は期間・単位・取得日時・出所を付け、初期は手動の振り返り欄で十分。

対照と結果を見ずにタイトルや音を全部変えず、次に変える一要素を記録する。OAuth・Analytics自動接続・汎用CSV取込・収益会計は後続。データ型と本人対象の識別を今分ければ、通常は全DB作り直しを必要としない。
