# 自動追跡・履歴・定期実行

> 文書ID：TRK-002\
> 状態：段階A/Bの実装を追加。検証・通常切替・実翌日観測はTRK-005の実施記録で区別。整理日：2026-10-16。\
> 依存：[TRK-001](README.md)、[POL-001](../compliance/data-retention.md)。

## 1. 登録と初回値

動画詳細の保存、取得時点の観測保存、自動追跡登録を同じDBトランザクションにする。ユニークな追跡単位は `データセット世代＋source＋動画ID`。US/JPや複数テーマで重複しても動画の追跡は一つにし、検索経路の所属は別で残す。

初回の実取得日時を基準に次回予定を24時間後へ設定する。0・1・9再生でも同じ動作。詳細取得に失敗したIDは初回未取得として復旧対象にし、架空の0再生を作らない。詳細の再生数がNULLでも追跡対象から落とさず、値がない理由を表示する。

初回値は投稿時点の値ではない。初回取得前の経過を復元しない。再発見や手動取得で初回日時を更新したり、元の観測値を新しい値で上書きしたりしない。検索が後に別動画を返しても、既に登録した動画を追跡対象から外さない。

## 2. 現在値・観測値・追跡状態を分離

物理テーブル名は実装時に確定する。既存の `targets` / `videos` / `channels` / `observations` を活用し、同じ役割の重複DBやテーブルを作らない。

| 責務 | 最低限の情報 |
|---|---|
| 現在値 | 最新に取得できた動画/チャンネルの公開情報と取得日時 |
| 不変の観測 | 対象ID、実取得日時UTC、各公開数値、取得種別、予定枠ID、取得実行参照、独立したexpires_at |
| 追跡管理 | データセット世代、初回取得日時、最終試行/成功、次回予定、追跡状態、停止理由 |
| 更新実行 | 予定対象、成功/欠損/失敗/未実行件数、再開位置、lease、予算、予定時刻と実時刻 |
| 稼働確認 | scheduler/workerのheartbeat、期限超過件数、最も遅れている予定、最終実行結果 |

観測の値は0なら0、非公開/欠損ならNULL。成功した同じ枠の再配信で観測を二重追加しない。例えば `(dataset_id, source, target_id, scheduled_for)` にDBユニーク制約を設ける。手動取得・初回取得にも別の冪等キーを持たせる。1日複数の正当な実取得は時刻で区別するが、画面の再表示やジョブ再試行では増やさない。

失敗ログを成功観測として保存しない。APIが200で対象を返さない場合、ネットワーク失敗、数値欠損は別の状態。非返却を削除・非公開と断定せず、現在の利用条件に沿って非表示/再確認する。確認された削除や利用取消についてはPOL-001を優先する。

## 3. 約24時間ごとの自動更新

初期方針は、初回取得時刻を基準に24時間間隔の予定枠を作り、schedulerが5分ごとに期限到来対象をDBキューへ渡すこと。5分は起動確認とバッチ化のための設計値であり、5分ごとに全動画のAPIを呼ぶ意味ではない。

- 最新mainの `watched=true` に限定する日次更新を置き換える。手動ウォッチは選択用で、解除しても自動追跡を停止しない。
- 「追跡を停止/再開」は別の明示操作とし、0再生や伸びないことを理由に停止しない。7日・28日を過ぎても一律終了しない。
- 予定時刻を未来へ移して遅延を隠さない。実取得時刻をそのまま保存する。
- 手動取得が到来済みの予定枠を満たせる場合は、同じ枠を重複消費しない。早い手動取得で翌日の予定を先送りしない。
- 停止中に複数枠を逃したら、復旧時に現在の値を一度だけ取得する。過去の予定枠には欠測を記録し、過去日時の観測値を捏造しない。
- 一回のジョブで全対象を無期限処理せず、小さいバッチと永続再開位置に分ける。成功済みを再取得せず、失敗対象だけ再試行する。
- 旧 `youtube:refresh-watch --daily` の日付一意キーで、その日途中に追加された新規対象まで処理済み扱いにしない。残す場合は同じ新追跡サービスへ委譲する互換入口にする。
- 関連チャンネルの統計も重複排除して日次更新する。動画統計の追跡を、毎日の投稿一覧巡回やキーワード再検索と結合しない。

## 4. 起動状態も完成範囲

`routes/console.php`、`compose.yaml`、workerのqueue選択を確認し、通常起動でWeb・DB・必要worker・schedulerが揃う手順をREADMEに記載する。schedulerを起動していないのに「自動追跡中」と表示しない。Composeの再起動方針、WSL/Dockerが起動している前提を明記する。

画面を閉じても動くこと、アプリの再起動時に未処理分が復旧することをテストする。PC/WSLが停止している間は取得できない。停止していた事実は履歴に残し、連続観測成功とは報告しない。常時稼働サーバーの新規契約・移行は今回行わない。

## 5. API予算と公平性

公開情報の更新は `videos.list` / `channels.list` のID指定を使う。`videos.list` のid指定に `maxResults` / `pageToken` を付けない。最大50IDずつのバッチという本プロジェクトの実装単位で、同一IDをまとめる。新APIへの移行は不要。[根拠](sources.md)

検索20/read500の既存アプリ設定と全処理共通の `api_days` を維持。失敗・再試行・消費不明も台帳に反映する。例として130動画を一巡する動画取得部分は、50ID単位なら最低3リクエストであり、130検索ではない。関連チャンネル取得・再試行は別途必要。

### 新規取り込みを保護する予算・再試行（2026-10-18）

追跡用キューの優先は維持するが、「到来した追跡が1件でもあれば検索を停止する」条件は廃止する。検索20/read500の日次総枠を引き上げず、次の制約を同じ `api_days` 行のロック内で送信前に検査する。設定の正本は `.env.example` / `config/youtube.php`。

- `YOUTUBE_DAILY_TRACKING_READ_CALLS` はread総枠の内数で既定100。失敗・再試行・消費不明も含めた追跡の送信試行を `tracking_read_calls` に加算する。総readと追跡readは一括で予約し、並列実行でも超過させない。
- `YOUTUBE_MANUAL_READ_RESERVE` は新規・手動取得に残す最低read枠で既定100。追跡の実効上限は `min(追跡上限, max(0, 総read上限 - 手動確保枠))`。手動取得は総枠まで利用できる。追跡以外による消費やGoogle側の停止まで防げる保証ではない。
- 到来済みかつ再試行待ちでない追跡だけについて、種類別の50ID読取数を予約する。予約は追跡の当日残枠を上限とする。検索はその予約に加え動画・チャンネル詳細の2要求分、手動読取は1要求分が共存できない場合にだけ `tracking_budget_reserved` で送信前に止める。
- 追跡上限・read総枠・Googleのquota停止中は、新しい追跡実行や連鎖ジョブを作らず、PTの翌日回復を待つ。予定時刻・未充足状態は残す。新規取得の検索枠は追跡では使わない。
- 移行前の用途別消費は復元できないため、既存行の追跡readは既存read総数から保守的に開始する。総read/search/blockedを初期化しない。用途別の厳密な内訳は移行後の送信分から有効。

再確認は次の間隔を守る。schedulerの5分起動はAPI再送の間隔ではない。対象の `last_attempt_at` と理由で判定し、worker再起動でも待機を維持する。

| 結果 | 自動再確認 |
|---|---|
| 正常 | 従来の約24時間予定 |
| API非返却、無効な要求/応答、キー・権限エラー、その他APIエラー | 最終試行から24時間後以降 |
| ネットワーク・一時障害・worker中断・競合等 | 呼出内の既有限リトライ後、最終試行から1時間後以降 |
| 日次上限・Google quota停止 | PTの翌日以降、共有枠の回復後 |

非返却を削除・非公開と断定せず、自動追跡対象には残す。成功観測や増分0を捏造せず、元の予定を将来へずらさない。待機対象は新規検索の予約計算から外し、他の正常対象の処理を妨げない。再試行で失敗枠を処理中へ戻し、成功した枠だけ充足する。予算で未送信になった別種類の対象には元の停止理由を引き継ぎ、非返却と誤表示しない。

画面にはアプリの総枠・追跡内訳・実効上限・最低手動枠と、追跡停止理由・対象の再確認可能時刻を表示する。Cloud Consoleの実残量とは区別する。低再生による間引き・追跡終了・別プロジェクトへの切替・自動上限引上げは行わない。対象増加により上限を超えれば、未充足の予定を残し翌日以降へ繰り越す。

## 6. 検索結果の期限と、観測履歴の期限を切り離す

現行の `Retention` は古い探索の `fetch_runs` を削除し、`observations.fetch_run_id` はcascadeOnDelete。このまま新しい観測を元探索へ結び付けると、探索期限で追跡用履歴まで消える。

各日次取得を独立した実行として保存し、観測のexpires_atをその観測の実取得時刻から計算する。関連の削除動作も見直し、古い検索run削除で期限内の新しい観測や追跡状態が消えないようにする。APIの期限切れ検索所属・順位を延命することも禁止。

アクティブな追跡対象は、利用者が今回まとめて追跡を指示した対象参照として維持する。検索結果が失効しても、更新済み公開情報と追跡は継続する。状態参照と過去のAPI統計を同一視しない。

## 7. 蓄積できる範囲を隠さない

現行のPOL-001に従い、競合の未認可統計は各観測点を28日ローリングで保持する。初回の観測値も例外ではなく、期限後は数値を削除し「初回値は保存範囲外」と表示する。初回値を別カラム・CSV・AIレポートへ移して延命しない。初回取得日時など自分の処理記録と、過去のAPI数値は別に管理する。

28日を超える全履歴の継続保存は、監査・追加許諾の確認を伴う別事項。今回それを許可済みと扱わず、取得日付の書換えで迂回しない。現行制約のままでも、追跡を続けて直近の毎日の履歴を蓄積できる。履歴期間の限界は画面と出力へ明記する。

## 8. 切替前に固定するデータ契約（AUD-003 A-02/03/05、採用・未実装）

論理契約 `tracking-data-v1`。各参照は同じdataset_id/sourceに属することをFKと取込検査で保証する。sourceはlive/demo、ownershipは本人宣言のown/competitor/unknown。所有宣言はAPI認可ではない。

| 領域 | 今回保存する項目・意味 |
|---|---|
| 動画観測 | view_count / like_count / comment_count。各値はnullable整数、0と非返却・非公開・取得失敗を区別するfield_statusを伴う |
| チャンネル観測 | view_count / subscriber_count / video_count。登録者数はAPIの丸め値である旨とhidden状態を残す |
| 動画メタデータ版 | title / description / tags / published_at / duration / liveBroadcastContent / defaultLanguage / defaultAudioLanguage / categoryId / thumbnails（URLと寸法）。返却されない項目はNULLと理由を残す。説明・タグは表示比較用で分類・学習用ではない |
| チャンネルメタデータ版 | title / published_at / uploads playlist ID。説明・キーワードは今回保存しない（用途確定後に追加）。作成日を運営開始日とみなさない |
| 版の識別 | metadata_version_id、対象参照、schema_version、正規化した項目のSHA-256、取得日時、expires_at。観測は観測時の版IDを参照する |
| 検索所属 | 対象参照、run/task、query/theme/lens/preset、検索日時・順位・取得範囲、catalog版、独立したexpires_at。多対多で保持し、観測の所有者にしない |
| 投稿発見の走査 | 注目チャンネル、uploads ID、走査開始/終了、確認日時、確認範囲、次ページ位置、未完理由、予算、期限。公開動画数の差を投稿数に変換しない |

メタデータは値が変われば新しい不変版を追加する。同値の再取得も既存版の取得日・期限を延ばさず、新たな取得証明として新しい版を作る。旧観測の版参照を書き換えない。最新表示は最新の有効な版を使い、期限切れ版の内容を隠して削除しても観測自体は独立した期限まで残す（版参照は失効状態にできる設計）。変更の実時刻は前回と今回の検出区間内としか分からない。

サムネイル画像本体の保存・画像ハッシュは今回無効。URLのハッシュを画像内容の証拠にしない。説明・タグ・数値・版の内容はPOL-001の期限対象。生のAPI応答全体は保存しない。

既知動画の統計更新、新規候補のEXP検索、注目チャンネルのuploadsによる投稿発見を別ジョブ・別進捗にする。お気に入り解除で既知動画の追跡を止めない。全関連チャンネルを毎日巡回して未登録投稿を発見する約束はしない。注目チャンネルの投稿確認は既存経路を維持し、明示操作・共有予算内でページ単位に再開する。未完範囲を「最新10本確認済み」にしない。発見後は通常の初回観測＋追跡登録を原子的に行う。

予算見積りは動画ceil(Nv/50)＋チャンネルceil(Nc/50)を基礎に、再試行・新規詳細・uploadsを別加算する。必要read予約と実測要求数を照合し、不足時は新規発見を待機させる。低再生を脱落させない。

## 実装時の物理契約（2026-10-16）

追加migrationは `database/migrations/2026_10_16_000003_create_tracking_contract.php`。既存行を消さず追加する。通常環境の新収集は一回の切替完了前に `cutover_required` で停止し、テスト環境だけ検証済み専用接続で先に実行できる。

| テーブル | 一意性・索引・保存責務 |
|---|---|
| datasets | UUID主キー、active=true部分一意索引、cutover_operation一意。完了履歴を保護し再消去を拒否 |
| targets / fetch_runs / explorations / comparisons | dataset_id FKを追加（旧行はNULL、新規処理は現世代を照合）。targetsのsource/kind/external_id一意を維持、ownershipを追加 |
| tracking_targets | target_id一意FK、dataset/state/next_due_at索引。active/pausedと理由、first_seen/last_success/last_attempt/next_dueを保持 |
| tracking_slots | dataset/target/scheduled_for一意、target/scheduled_for/state索引。pending/fulfilled/failed/missedとfulfilled_at。欠測に観測値を作らない |
| metadata_versions | target/fetched_at索引、期限索引。許可項目のJSONB、SHA-256、取得時刻・期限。画像実体は保存しない |
| observations | target/fetch_run一意を維持、tracking_slot_id一意FK、target/fetched_atと期限索引。検索run FKはSET NULL、版/枠削除もSET NULL。各点の値・field_status・origin・scheduled_forを保持 |
| tracking_heartbeats | name主キー、scheduler/workerのseen_at。900秒を超えたら未稼働/期限超過表示 |
| comparisons | 固定evidence JSONBとas_of/期限、analysis JSONBとanalysis_revision/state/template_version。期限でAPI根拠と分析本文を消す |
| production_briefs | comparison FK、dataset/source、分析版、本人企画と手動振り返りJSONB、revision。既存比較や分析の変更で上書きしない |

観測のfield_statusはreturned/not_returned/hidden。追跡理由はuser_paused、downtime、not_returned、既存API失敗コード、tracking_budget_reserved等。詳細が返らない場合は過去値を0へ変えず、追跡参照と予定は維持する。冪等な枠・トランザクション・対象行ロックで二重保存を防ぐ。追跡ジョブはtrackingキューを優先し、1ジョブ50対象、未処理は次ジョブへ、失敗は5分後以降に再試行する。関連チャンネルは独立した追跡対象としてまとめ、日次更新ではuploadsを走査しない。

注目チャンネルの新規投稿発見は既存の直接登録/uploads・続き取得を維持する。確認runに件数・nextPageToken・listing_done・取得日時を残す。これは既知動画更新とは別操作であり、未走査を最新投稿全体としない。

関連チャンネルは詳細が未取得でもpending相当の追跡参照を作り、last_success_atをNULLで保持して再確認する。metadataの各採用キーもNULLとfield_statusで返却有無を区別する。comparison_target.positionで本人の選択順を固定する。--daily互換入口も新ジョブへ委譲し、残件は優先キューで継続する。

分析の版はanalysis_revisions（UUID主キー、comparison_id/revision一意、期限索引）へ追記し、comparisons.analysisは最新入力の表示用とする。production_briefsのcomparison_id/analysis_revisionはその一意キーをFK参照する。分析を編集しても既存試作の参照版は変えない。期限後は各版の本文をNULLにし、本人企画を結ぶ内部参照だけを失効状態で保持する。
